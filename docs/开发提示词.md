## 1. 项目目标（一句话）

做一个**只有我们几个人用**的 Android 应用：我在自己手机上输入文字 / emoji / 图片 / 语音 / 手写涂鸦并指定发给某位朋友，**对方手机屏幕顶部会立刻弹出一条半透明的"玻璃质感"横幅**显示这条内容（约 5 秒后自动消失）；对方看到后点掉横幅，我这边能看到"已查看"。反向同样成立 —— 朋友发给我时，我的手机上也会弹，并在横幅上标注**是谁发的**。

**本质**：这是一款"轻打扰的即时表情传递器"，不是聊天软件。它借用 ntfy 的公共推送通道，但**界面与显示方式完全自研**。

## 1.1 非目标（明确不做，别自作聪明加）

- ❌ 不做端到端加密（用户已确认不需要）
- ❌ 不做群组/多人广播（只做"我 ↔ 每位朋友"的点对点）
- ❌ 不做多设备同步 / 云端账号体系 / 登录注册
- ❌ 不上架 Google Play 或国内商店（只侧载 APK）
- ❌ 不做 iOS / 桌面端
- ❌ 不做端到端消息撤回、消息编辑、消息引用
- ❌ 不依赖 FCM / Firebase（保持零 Google 服务依赖，国产 ROM 上更可靠）
- ❌ 不申请无障碍（Accessibility）权限（会被系统判为高危；悬浮窗方案已足够）

## 2. 已确认需求决策表（12 项，后续开发不得擅自更改）

| # | 议题 | 已确认决策 |
|---|---|---|
| 1 | 核心架构 | **复用 ntfy 服务端与协议 + 只自研 Android 客户端**（服务端不上自建） |
| 2 | 关系拓扑 | **星型**：只有"创建者（我）"对 **2～3 位朋友**；朋友只与创建者通信；每人**单设备** |
| 3 | 频道隔离 | **每位朋友一条独立私密频道（topic）**；创送时用"朋友列表"选人；**不做群发按钮**；朋友发来的消息**必须在横幅上标注发送者** |
| 4 | 显示形态 | **系统悬浮窗**（`SYSTEM_ALERT_WINDOW` / `TYPE_APPLICATION_OVERLAY`）；**不要求锁屏/息屏唤醒**；每条 **5 秒**自动消失；**无声音、无振动** |
| 5 | 发送端入口 | **App 内页面 + 常驻可拖拽悬浮球**；表情 = **系统 emoji + 内置表情面板 + 自定义表情包（图片）**；内容 = **文字 / 图片 / 语音 / 手写涂鸦**；**无快捷短语**；**无发送前预览** |

| 7 | 服务端 | **公共 ntfy.sh**（创建者无 VPS / 无域名）；**超长随机 topic 名当密码**；**不做加密** |
| 8 | 技术栈 | **Kotlin + Jetpack Compose**；**minSdk 29 / targetSdk 36 / compileSdk 36**；**只侧载 APK**；需要**协助搭建整套开发环境** |
| 9 | 弹框视觉 | **顶部横幅**（状态栏下方，避免遮挡）；高度自适应内容、**最大不超过屏幕 40%**；**毛玻璃 + 亚克力/高光玻璃边缘**；多条消息**排队依次显示**（每条各 5 秒） |
| 10 | 消息细节 | 图片 = **框内缩略图**（点开大图可后续再说，本期点即消失）；语音 = **波形 + 时长，点击播放，录制最长 20 秒**；涂鸦 = **框内显示，且对方能看到笔迹逐笔回放**；**点击气泡 = 立即消失且不打开 App**；**需要通知我"对方点掉了气泡"**；回执 = **朋友头像旁的**状态点** |
| 11 | 配对 | **邀请码文本**（我生成 → 微信发给朋友 → 他在 App 里粘贴）；**要权限向导页**；**不要 Demo 预览**；**朋友列表不提供增删/重命名管理**；**topic 名对朋友完全不可见** |
| 12 | 保活与通知 | **极简静默常驻通知**；文案随时间变化（如"早上好 <名字>"、"中午好 <名字>"、"晚上好，<名字>，天天开心"）；**开机自启**；**断线用 `since=` 补齐**；**指数退避重连 + 网络恢复立即重连**；**不做暂停开关**；常驻通知**不显示未读数** |

### 2.1 【假设】（实现前请向我确认，若我不回复则按此默认）

1. **创建者仍需"邀请新朋友"的入口**：朋友列表虽不做"增删管理"，但创建者必须能生成新的邀请码。默认实现为：设置页 → "邀请新朋友" → 生成一个新频道 + 一段邀请码；生成后该朋友出现在列表里，**不提供删除与重命名**。
2. 创建者端在首次进入时走一次"我是创建者"的角色设定；朋友端通过**粘贴邀请码**自动成为"朋友"角色（列表里固定只有 1 个人）。
3. 朋友端显示的名字 = 邀请码里携带的创建者名字，可在朋友的"设置"里改本地备注（不影响对方）。
4. 最大朋友数按 **5** 个设计（够用且便于做列表 UI）。

## 3. 用户流程（必须严格按此实现）

### 3.1 创建者首次启动
1. 欢迎页 → 选"我是创建者" → 输入自己的昵称（如"Eric"）。
2. 进入**权限向导**（见 3.6）。
3. 进入主界面：**朋友列表为空** + 一个醒目的"邀请朋友"按钮。

### 3.2 配对（邀请码）
1. 创建者点"邀请朋友" → App 生成一条**新的随机 topic**（见 6.4 命名规则）→ 展示一段**邀请码**（见 6.5 编码格式）+ "复制"按钮。
2. 创建者通过微信把邀请码发给朋友。
3. 朋友装好 APK，首次启动选"我是朋友" → 进入粘贴页 → 粘贴邀请码 → 点"配对"。
4. 朋友端解析出：服务器地址、topic、创建者的 uid 与昵称；然后**自动生成自己的 uid 与昵称**。
5. 朋友端立刻向该 topic 发布一条 `k=hello` 信封（见 6.3）宣告自己的 uid / 昵称 —— **同时**自己也已订阅该 topic。
6. 创建者端收到 `hello` → 自动把该朋友加入列表（显示昵称 + 头像占位 + 回执状态点）→ **无需任何手动操作**。
7. **幂等**：重复收到 `hello`、或朋友重装 App 后 uid 变化，都应以"更新已有朋友"处理，不得产生重复条目。

### 3.3 发送消息（创建者视角，朋友端完全对称）
1. 打开 App → 朋友列表 → 点某位朋友 → 会话页（显示最近 100 条历史）。
2. 底部输入区：文本输入框、emoji 面板按钮、自定义表情包按钮、图片按钮、语音按钮（长按说话 / 点击录制）、涂鸦按钮（进入全屏画布）。
3. 点发送 → 立刻在会话里插入一条"发送中"（灰点）的消息 → 走 `6.3` 的两段式发布 → 发布成功后状态变为"已发出"。
4. 收到对方 ack → 状态点变化（见 3.5）。
5. **悬浮球路径**：任意界面点悬浮球 → 展开一个紧凑输入面板（半透明浮层）→ 选朋友（默认上次那位）+ 输入 → 发送 → 面板收回。**该面板必须能正常唤起输入法。**

### 3.4 接收与弹框（对方视角）
1. 常驻前台服务保持对每位朋友 topic 的订阅（`/<topic>/json` 流）。
2. 收到消息 → 解析信封 → 若是 `k=msg`：按 `kind` 下载附件（图片/语音）或直接用文本/笔画数据 → **入队**。
3. **弹框队列**：一次只显示一条；每条显示 5 秒（进度条/淡出动画）后自动消失，然后显示下一条。收到消息后**立即**发送 `state=delivered` 回执（时机 = 悬浮窗成功加入 WindowManager 并完成首帧绘制之后，见 3.5 定义）。
4. 弹框内容布局（自上而下）：
   - 第一行：发送者昵称（小字，半透明白）+ 右侧一个小"×"（点掉）
   - 主体：文本 / 图片缩略图 / 语音条（波形 + 时长 + ▶）/ 涂鸦动画
   - 气泡整体：大圆角（24dp+）、毛玻璃或降级半透明深色、亚克力高光边缘
5. 用户**点一下气泡任意处** → 气泡立即消失（不打开 App）→ 发送 `state=dismissed` 回执（只发一次，若期间已被 5 秒超时关闭则不重复上报，见 6.3）。
6. **本地不留痕之外的副作用**：弹框消失后消息仍保存在会话历史里（本地最近 100 条）。

### 3.5 回执（状态点）定义 —— 精确语义
| 状态 | 触发条件 | 头像旁状态点 |
|---|---|---|
| 发送中 | 本地已插入，尚未收到 ntfy 发布成功响应 | 灰色空心点（脉冲动画） |
| 已发出 | ntfy 返回 2xx 且拿到消息 id | 灰色实心点 |
| **已送达** | 对方客户端**成功把悬浮窗加入 WindowManager 并完成首帧**，回发 `state=delivered` | **绿色点**（亮起，即用户说的"点一下亮起"的视觉效果） |
| **已查看/已点掉** | 对方**手动点掉**气泡，回发 `state=dismissed` | **蓝色点 + 小提示条**："小A 点掉了你的消息" |
| 失败 | ntfy 返回非 2xx 或重试 3 次仍失败 | 红色点 + 点击可重发 |

**注意**：5 秒超时自动消失**不算"已查看"**（用户明确说只关心"对方点掉了气泡"这一动作）。超时消失时**不回发**任何回执。

### 3.6 权限向导页（朋友端必做，创建者端同样走一遍）
按顺序、一屏一项、每项都要"当前状态检测 + 一键跳转 + 自动回检"：
1. **通知权限**（Android 13+ `POST_NOTIFICATIONS` 运行时申请）→ 目的：常驻通知与降级通知。
2. **悬浮窗权限**（`Settings.canDrawOverlays()` → `ACTION_MANAGE_OVERLAY_PERMISSION`）→ **最核心**，没有它一切白搭。
3. **电池优化白名单**（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，仅作引导，检测用 `PowerManager.isIgnoringBatteryOptimizations`）。
4. **国产 ROM 后台自启引导**（小米/华为/OPPO/vivo 的"自启动""后台弹出界面""锁定后台"）→ 用 `Intent` 尝试跳转对应设置页，**失败时给出图文说明让用户手动找**（不要因为跳转失败而崩溃）。
5. **每项完成后打勾**，全部完成才进入主界面；允许"稍后设置"（但主界面顶部常驻一条红色警告条："悬浮窗权限未开启，你收不到弹框"）。

## 4. 技术选型与工程结构

### 4.1 版本与配置
- 语言/UI：**Kotlin 2.x + Jetpack Compose + Material 3**
- 构建：**Gradle Kotlin DSL + Version Catalog**（`libs.versions.toml`）
- `compileSdk = 36`、`targetSdk = 36`、`minSdk = 29`

- **版本号策略**：不要手写 AGP/Kotlin/Compose 版本号猜版本，**由 Android Studio 新建项目向导生成的 version catalog 为准**（见第 9 章），只在其基础上加依赖。

### 4.4 架构约定
- **单向数据流**：UI → ViewModel → Repository → (Room / NtfyClient)；UI 只收 `StateFlow`。
- **服务是唯一网络真源**：`LinkService` 持有所有 topic 的订阅与重连逻辑；UI 不直接订阅 topic。UI 通过 `Room` 与 `StateFlow`/`SharedFlow`（进程内事件总线，如 `AppEvents`）与服务通信。
- **弹框与历史解耦**：收到消息先落库（Room），再由 `OverlayService` 从队列出栈显示；**即使悬浮窗权限没开，历史也必须正确落库**（这是验收项）。
- **所有跨进程 UI 操作都走 Service + WindowManager，不用 Activity**（Android 15 后台启动 Activity 受限）。

## 5. 视觉与交互规范（UI Spec）

### 5.1 弹框（Overlay Bubble）—— 本项目最核心的规范
- **位置**：屏幕**顶部**，距状态栏底边 8dp；左右各 12dp。**绝不能遮住状态栏**。注意：在 overlay 窗口里 WindowInsets 拿不到状态栏高度，**必须用 resources.getIdentifier("status_bar_height", "dimen", "android") 取**，取不到时兜底 24dp。
- **宽度**：铺满可用宽度（左右各留 12dp）。
- **高度**：内容自适应，**上限 = 屏幕高度 × 0.40**；超长文字省略号，图片/涂鸦等比缩放。
- **圆角**：28dp。**边缘**：1dp 内描边（白色 22% 不透明）+ 顶部高光渐变（白 12% → 透明，在 35% 高度处结束）+ 底部 2dp 深色内阴影。
- **底色**：绝对色值 #E6151619（约 90% 不透明深灰黑）；正文 #F2FFFFFF；发送者昵称 #B3FFFFFF、13sp。
- **亚克力质感配方（统一配方，不按版本分叉）**：
  1. 半透明深色底（上面的色值）
  2. 顶部高光渐变层
  3. 1dp 白色内描边
  4. 可选细微噪点纹理（res/drawable/noise.png 平铺，透明度 4%–6%）
  5. 外部投影：Compose 的 Modifier.shadow(20.dp, shape)，颜色纯黑
- **技术真相【必须理解，别写错】**：Android 第三方应用**无法对"窗口背后"的内容做真实背景模糊**（那是系统合成器的特权）。RenderEffect.createBlurEffect 只能模糊**本窗口自己的内容**。因此：
  - **不要**试图去模糊"对方屏幕上的微信"，做不到，别浪费时间；
  - API 31+ 可用 RenderEffect 给**卡片内部装饰层**（高光层/噪点层）做轻微柔化（半径 6–10），观感更像玻璃；API 29/30 跳过该步，用同样的底色+描边，**观感差异小于 5%，不会白屏、不会崩**；
  - 代码形态：AcrylicSurface(blurInner = Build.VERSION.SDK_INT >= 31)。
- **入场动画**：自顶部 -20dp 滑入 + 透明度 0→1 + 缩放 0.96→1，220ms，FastOutSlowInEasing；出场：透明度 1→0 且上移 -12dp，180ms。
- **进度提示**：气泡底部一条 2dp 细进度线，5 秒内从左走到右，让接收者知道还剩多久。
- **点击行为**：整条气泡可点 → **立即消失**（不打开 App、不展开详情）→ 触发 dismissed 回执。
- **关闭按钮**：右上角 20dp 半透明"×"，效果等同点击气泡。
- **不做**：拖动、长按菜单、气泡内回复按钮。

### 5.2 悬浮球（Floating Ball）
- 直径 48dp；默认停靠屏幕右侧、垂直位置约为屏幕高度的 65%；半透明深色 + 白色图形图标（说话气泡造型）；阴影 8dp；整体不透明度约 70%，避免刺眼。
- **可拖动**：拖动期间不响应点击；松手后**吸附到最近的左/右边缘**，并把 Y 坐标**持久化**（DataStore）。
- **手势冲突处理**：若吸附位置落在系统返回手势区域（距屏幕底边 24dp 内、或左/右边缘 16dp 内），自动向内偏移 24dp。
- 点击悬浮球 → 展开**紧凑输入面板**（宽 300dp，优先显示在球体上方，空间不足则下方）：
  - 顶部：当前目标朋友（头像 + 昵称，点击可切换）
  - 中部：单行输入框 + emoji 按钮 + 图片按钮 + 语音按钮
  - 底部：发送按钮（大、圆角、主色）
  - **该窗口必须 focusable 且能唤起输入法**（实现细节见 7.4）
- 展开面板时**暂停弹框队列**（不让对来的消息盖住输入面板）。
- 点击面板外区域 → 收起；内容为空点发送 → 轻微抖动提示，不发送。

### 5.3 会话页与朋友列表
- 朋友列表每行：圆形头像（昵称首字 + 由 uid 稳定散列出的颜色）+ 昵称 + **右侧状态点（见 3.5）** + 最近一条消息摘要 + 时间。
- 会话页：气泡左右分栏（我右、他左），支持文本 / 图片 / 语音条 / 涂鸦静态图；语音条点击播放（优先本地文件，缺失时用远端 URL）。
- 会话页顶部：返回 + 朋友昵称 + **连接状态小圆点**（绿=已连接、黄=重连中、红=失败；点击可手动重连）。
- 空态：引导文案"点这里邀请朋友"。

### 5.4 emoji 与自定义表情包
- **系统 emoji**：直接交给系统输入法，不重复造轮子。
- **内置 emoji 面板**：4 行 × 8 列共 64 个常用 emoji（😀😂🥰😎🤔😭🤯🙏👍❤️🔥🎉 等），点击插入文本。
- **自定义表情包**：相册选图或拍照 → 存本地 filesDir/stickers/ → 面板显示缩略图 → 发送时 kind=sticker（走图片通道，但渲染时**不显示发送者昵称**、尺寸更小、圆角更小）。

### 5.5 涂鸦（Doodle）
- 全屏画布（普通 Activity 内即可，**不需要悬浮窗**）：6 色色板、3 档笔宽、橡皮、撤销、清空。
- 笔画采集：color（ARGB）、width（相对画布宽的比例）、points（归一化 0..1）、tStart/tEnd（毫秒，相对画布打开时刻）。
- **逐笔回放**：接收端按 tStart 升序重放，**总时长压缩为 min(原始时长, 2500ms)**；每笔沿折线按段长匀速推进，避免长线段瞬间跳完。
- 体积：笔画 JSON **超过 3.5 KB** 时必须改为上传 .json 附件（见 6.6）。

### 5.6 主题
整个 App 默认深色；弹框永远是深色玻璃质感，**不跟随系统浅色模式**。

### 6.2 自定义信封协议 NtfyPop Envelope v1（**自己定义、必须严格实现**）

我们**不修改 ntfy 协议**，而是把 ntfy 的"消息正文"当传输层，正文里放我们自己的 JSON 信封。**任何无法解析为本信封的正文一律丢弃**（例如上传附件时产生的那条原始消息）。

~~~json
{
  "v": 1,                      // 协议版本，固定 1
  "k": "msg",                  // msg | ack | hello
  "mid": "c-7f3a9b21",         // 客户端消息 id：c- 前缀 + 8 位随机 hex，全局唯一（幂等键）
  "from": "u_9b2c41",          // 发送方 uid（安装时生成，永不变）
  "name": "Eric",              // 发送方昵称（弹框标注用；接收方以本地备注优先）
  "to": "u_e7a10d",            // 接收方 uid
  "ts": 1761350000000,         // 客户端毫秒时间戳
  "kind": "text",              // text | emoji | sticker | image | voice | doodle
  "text": "你好",               // kind=text/emoji 时必填
  "blob": {                    // kind=image/voice/doodle/sticker 且已上传附件时必填
    "url":  "https://ntfy.sh/file/xxxxxxxxxx.png",
    "name": "img_7f3a.png",
    "mime": "image/png",
    "size": 33848,
    "w": 1080, "h": 1440,      // 仅 image/sticker
    "dur": 5200,               // 仅 voice，毫秒
    "peaks": [0.12, 0.55, 0.31] // 仅 voice，32 个 0..1 浮点
  },
  "strokes": [ ],              // 仅 doodle 且体积小（不超过 3.5KB）时内联，结构见 6.7
  "ref": "hwQ2YpKdmg"          // 附件那条 ntfy 消息的 id（便于排查）
}
~~~

**ack 信封**（回执；**必须静默**：收到 ack 的一方不得弹框、不得再回 ack，避免回执风暴）
~~~json
{ "v":1, "k":"ack", "mid":"c-7f3a9b21", "from":"u_e7a10d", "to":"u_9b2c41",
  "ts":1761350005000, "state":"delivered" }
~~~
state 取值：delivered（已送达） | dismissed（对方点掉了气泡）。

**hello 信封**（配对完成后的第一件事，用于让对方端自动建立好友项）
~~~json
{ "v":1, "k":"hello", "mid":"c-0000a1b2", "from":"u_e7a10d", "name":"小A",
  "to":"u_9b2c41", "ts":1761350000000, "kind":"text", "text":"" }
~~~

**兼容性规则**：收到 v 大于 1 的信封 → 忽略并在 UI 提示"对方 App 版本过新"；收到缺字段的信封 → 忽略并记日志，**绝不能崩**。

### 6.3 发送流程（**两段式，必须按序**）

> **为什么两段式**：ntfy 的附件消息正文被文件内容占用，没地方再塞我们的元数据；因此把"文件"和"信封"拆成两条 ntfy 消息。

**文字 / emoji（单条）**
1. POST {server}/{topic}，正文 = 信封 JSON；请求头：Title = 发送者昵称、Priority = 3、Cache = yes、Content-Type = application/json。
2. 读响应 JSON 取 id（服务端消息 id）→ 落库为 serverId → 状态置 SENT。
3. 非 2xx：按 6.8 退避重试 3 次；仍失败置 FAILED（UI 红点 + 可重发）。

**图片 / 语音 / 涂鸦 / 表情包（两条）**
1. PUT {server}/{topic}，正文 = 文件二进制；请求头：Filename = 安全文件名、Title = __blob__、Priority = 1。读响应取 blobServerId 与 attachment.url。
2. POST {server}/{topic}，正文 = 信封 JSON（blob.url 填上一步 URL、ref 填 blobServerId）；请求头：Title = 发送者昵称、Priority = 3。
3. 两步都各自重试；**若第 1 步成功而第 2 步最终失败**：UI 必须明确提示"媒体已上传但信封未发出"并提供重发按钮，**不得静默丢弃**。
4. **接收方**：遇到 Title = __blob__ 或正文无法解析成信封的消息 → **直接忽略：不弹框、不入历史**（只记日志）。

**接收方渲染顺序**：先解析 kind → 需要媒体则**异步下载**（**先弹框并显示占位骨架/进度，下载完成后就地替换，不要因为下载慢就不弹框**）→ 弹框完成 → 立即回 delivered。

### 6.4 topic 命名规则
- ntfy 允许字符：字母、数字、下划线、连字符，长度 1–64。
- 我们的格式：np1_ + SecureRandom 生成的 **22 位 Crockford Base32**（剔除易混字符 I、L、O、U）→ 总长 26 字符。
- **每位朋友一条 topic**，彼此独立；创建者与朋友**共用同一条 topic 双向收发**（双方都订阅、都发布）。
- **回显过滤**：收到信封时若 from 等于本机 uid → **丢弃**（双方订阅同一 topic，必然收到自己发的消息）。
- **topic 名永远不出现在常规界面**（用户明确要求），只存在于设置页"配对信息"中可复制。

### 6.5 邀请码编码（用户选了"文本邀请码"）
- 明文载荷（紧凑 JSON，无空格）：{"v":1,"sv":"https://ntfy.sh","tp":"np1_xxxx","uid":"u_9b2c41","nm":"Eric"}
- 编码：NTP1- 前缀 + Base64URL(UTF8(payload))（Base64URL 使用 - 与 _ 变体，并**去掉填充等号**）
- 解析要**宽容**：允许前后空白与换行、允许缺失 NTP1- 前缀、允许微信插入空格（解析前先删除所有空白字符）。
- 解析失败 → 明确提示"邀请码不完整或已损坏"，**不要崩**。
- 补充假设：创建者端设置页保留"邀请新朋友"入口（生成新 topic + 新邀请码），但不做删除/重命名。

### 6.6 大小与体积约束（硬性）
| 内容 | 上限 | 落地策略 |
|---|---|---|
| 文字 | 4096 字节（ntfy 硬限） | 输入框限制 **1200 字符**（中文 UTF-8 约 3 字节/字，4500 字节会超限），超限即时提示 |
| 信封正文（含 strokes） | 3500 字节 | 超限时把 strokes 转成 .json 附件上传（blob.mime = application/json），信封只留 blob 引用 |
| 图片 / 表情包 | 压缩后不超过 1.5 MB | 长边不超过 1600px、JPEG 质量 85%；透明 PNG 保留 PNG 但压到不超过 1MB，否则转 JPEG + 白底 |
| 语音 | 20 秒 | AAC-LC / MPEG_4 / 单声道 / 16 kHz / 32 kbps（20 秒约 80 KB） |
| 涂鸦附件 | 不超过 500 KB | 坐标取整 + 抽稀（相邻点距离小于 1.5px 则合并） |

### 6.7 涂鸦笔画结构（内联与附件共用同一结构）
~~~json
[ { "c": "#FFFFFFFF", "w": 4.0, "t0": 0, "t1": 820,
    "p": [[0.12,0.31],[0.13,0.33],[0.15,0.36]] } ]
~~~
- p 为归一化坐标（0..1，基于画布宽高）；c 为 ARGB 十六进制字符串；w 为逻辑笔宽（相对画布宽 1080 的比例）。
- 回放：按 t0 升序；总时长取 min(最大 t1, 2500ms)；画布宽高比取自信封 blob.w/h，内联时默认为 16:9 居中适配。

### 6.8 断线、重连与补齐（**"不漏消息"的关键**）
1. 每个 topic 维护 lastServerId（最后成功处理的消息 id）与 lastServerTime，持久化到 DataStore。
2. **连接建立流程**：先 GET /{topic}/json?poll=1&since={lastServerId} 拉取离线消息（按 ts 升序处理，去重靠 mid）→ 再 GET /{topic}/json 开长连接。
   - 首次配对时 lastServerId 为空：用 since=1h（避免拉回一堆无关历史）。
3. **心跳判活**：ntfy 流会定期发 event=keepalive；若 **90 秒**内没收到任何事件（含 keepalive）→ 判定假死 → 主动断开重连。
4. **重连退避**：1s → 2s → 4s → 8s → 16s → 30s（封顶），每次加正负 20% 抖动；**网络恢复回调（NetworkCallback.onAvailable）立即重置退避并重连**；App 回前台、屏幕点亮也各触发一次重连检查。
5. **并发**：每个 topic 一条独立订阅协程，统一挂在 SupervisorJob 下，一个 topic 挂掉不影响其它。
6. **错误分类**：
   - 4xx（429 除外）→ 不重试，UI 提示（多为 topic 名非法或服务器地址写错）
   - 429 / 5xx / 网络异常 → 走退避重试
   - 响应头含 X-Messages-Truncated: 1 → 补发被截断，记日志后继续
7. **重复消息**：Room 的 mid 建唯一索引，插入用 IGNORE 冲突策略；**弹过框的消息绝不重复弹框**（以 mid 为准，不以服务器 id 为准）。

### 6.9 幂等与顺序
- mid 是唯一幂等键；hello 重复到达只更新不新建朋友项。
- 弹框顺序 = 收到顺序（同一 topic 内按 ts 排序后入队，跨 topic 不保证全局有序）。
- 本地时间戳只用于显示与排序，**不得回改系统时间**。

## 7. 关键模块设计细则

### 7.1 NtfyClient（发布 / 上传 / 下载）
- 单例 OkHttpClient：connectTimeout 10s、writeTimeout 30s、**readTimeout 0（长连接必须）**、pingInterval 关闭。
- publishEnvelope(topic, envelopeJson): POST {server}/{topic}，头见 6.3；返回 serverId 或抛错。
- uploadFile(topic, bytes, filename, mime): PUT 二进制；返回 Pair(serverId, attachmentUrl)。
- download(url, destFile, onProgress): 流式写入，**硬性大小上限 15 MB**，超过即中止并报错；下载目录 filesDir/media/。
- **日志脱敏**：topic 名只打印前 6 位 + 星号；uid 同理。**禁止把完整 topic 写进 Logcat**（它等同于密码）。

### 7.2 NtfyStream（订阅）
- 用 OkHttp 的流式响应（ResponseBody.source），**逐行读取**（readUtf8Line）。
- 以 callbackFlow 暴露 Flow<NtfyEvent>；收到 open / message / keepalive 三类事件都向上发（keepalive 用于判活）。
- 单行 JSON 解析失败 → 记日志跳过，**不断流、不崩**。
- 取消订阅时关闭连接；异常向上抛给 LinkService 决定是否重连。

### 7.3 LinkService（前台服务 = 大脑）
职责（**全部在这里，UI 不碰网络**）：
1. 启动时读取朋友列表（Room）与 lastServerId（DataStore），为每个 topic 建订阅协程。
2. 收消息 → 解析信封 → 分派：
   - k=msg：幂等检查（mid 是否已存在）→ **先落库** → 移交 OverlayController 排队显示（**无悬浮窗权限时只落库 + 发一条降级通知**）→ 显示完成后回 delivered。
   - k=ack：更新对应 outbox 状态；若 state=dismissed → 发一条**静默通知**（无声音、无振动、正文"某某 点掉了你的消息"）+ 在朋友列表头像旁显示蓝点。
   - k=hello：新建或更新朋友项（幂等），并回一条 ack（可选，用于对方确认配对成功）。
3. 连接状态维护（已连接 / 重连中 / 失败）→ 通过 AppEvents 广播给 UI。
4. 常驻通知维护（见 8.4），文案随时间问候。
5. 退出/被系统杀死时：onTaskRemoved 不做任何"自杀"处理；依赖 START_STICKY 与开机自启恢复。
6. **不持有 WakeLock 常驻**（耗电）；网络不可用时靠 NetworkCallback 唤醒重连。

### 7.4 OverlayController：把 Compose 放进 WindowManager（**本项目最大的技术坑，必须按此写**）
1. **不要用 Activity 承载弹框**（Android 15 后台启动 Activity 受限，且会打断用户）。由 LinkService 初始化一个进程级单例 OverlayController，用 Application 级的 WindowManager 加窗口。
2. **窗口参数**：
   - type = TYPE_APPLICATION_OVERLAY（API 26+）
   - format = PixelFormat.TRANSLUCENT
   - flags = FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCH_MODAL（**弹框不抢焦点**）
   - gravity = TOP | START，x = 12dp，y = 状态栏高度 + 8dp
   - width = MATCH_PARENT，height = WRAP_CONTENT
   - **不要用 FLAG_LAYOUT_NO_LIMITS**（容易越界到状态栏/导航栏）
3. **ComposeView 的生命周期**：Compose 的 ViewTreeLifecycleOwner 在 WindowManager 里是空的，**必须自己实现一个 OverlayLifecycleOwner**（内含 LifecycleRegistry、ViewModelStore、SavedStateRegistryController），用 setViewTreeLifecycleOwner / setViewTreeViewModelStoreOwner / setViewTreeSavedStateRegistryOwner 挂到 ComposeView 上；移除窗口时必须 disposal（防止协程泄漏与内存泄漏）。
4. **复用窗口**：队列显示时**复用同一个窗口与 ComposeView**，只切换内部数据与做进出场动画，避免反复 addView/removeView 造成闪烁。
5. **悬浮球与输入面板**：窗口需要接收键盘输入，因此：
   - 去掉 FLAG_NOT_FOCUSABLE；保留 FLAG_NOT_TOUCH_MODAL**（错误：不要设 FLAG_ALT_FOCUSABLE_IM）**
   - softInputMode = SOFT_INPUT_ADJUST_RESIZE
   - 展开面板后请求焦点并软键盘显示：InputMethodManager.showSoftInput(view, SHOW_IMPLICIT)
   - **面板收起时必须恢复 FLAG_NOT_FOCUSABLE**，否则会抢走当前 App 的输入（用户正在微信打字会被打断，属于严重体验问题）
   - 悬浮球本身点击不抢焦点，仅在展开面板时切为可聚焦
6. **首帧回调**：用 doOnPreDraw 或 addOnGlobalLayoutListener 判定"真正显示出来了"，**此时才回 delivered 回执**（3.5 的定义）。
7. **权限缺失的降级**：Settings.canDrawOverlays 为 false 时，OverlayController 不可用时**不得崩溃**，改为发一条普通通知（标题 = 发送者，正文 = 内容摘要），并在 App 内顶部显示红色警告条。

### 7.5 弹框队列（OverlayQueue）
- 数据结构：ArrayDeque + Mutex（或 Channel），**串行**：一次只显示一条。
- 每条生命周期：入场动画 220ms → 静态展示 5 秒（进度线同步走）→ 出场动画 180ms → 下一条。
- 用户点击 → 立即出场并把该条标记为"手动点掉" → 发送 dismissed 回执（**只发一次**；若同一 mid 已被 5 秒超时关闭则不补发）。
- 队列上限 10 条；溢出时丢弃最旧的并在日志记录（**不弹"消息过多"的提示**，避免打扰）。
- 展开悬浮球输入面板时**暂停出队**（保留队列，面板收起后继续）。


### 7.6 本地存储设计（**v1 不用 Room，改用轻量 JSON 存储**）
- **为什么不用 Room**：Room 依赖 KSP，而 KSP 与 Kotlin 版本强耦合，是本机最容易构建失败的环节；本项目数据量极小（最多 5 个好友、每人最多 100 条），kotlinx-serialization 加原子写 JSON 文件完全够用，还少两个构建期依赖。
- **存储位置**：filesDir/data/
  - peers.json —— 好友列表
  - messages_<peerUid>.json —— 按好友分文件，每人只留最近 100 条
  - outbox.json —— 发送中/失败的待重试队列
  - settings —— 用 DataStore Preferences（selfUid / selfName / role / serverUrl / 每个 topic 的 lastServerId）
- **数据模型**（Kotlin @Serializable data class）
  - Peer(uid, topic, localAlias, remoteName, avatarColor, createdAt, lastSeenAt, lastState)
  - Message(mid, peerUid, direction, kind, text, blobJson, strokesJson, localMediaPath, remoteUrl, serverId, tsClient, tsServer, state, deliveredAt, dismissedAt)
  - OutboxItem(mid, peerUid, payloadJson, attempts, lastAttemptAt, lastError)
  - Sticker(id, filePath, createdAt, lastUsedAt)
- **写入纪律**：一律先写临时文件、再原子替换（避免进程被杀导致 JSON 损坏）；解析失败时把坏文件改名备份并回退到空集合，**绝不崩溃**。
- **保留策略**：每个好友只保留最近 **100** 条；删除记录时同步删除其本地媒体文件（避免存储无限增长）。
- **并发**：所有读写收口到一个单例 Store（内部 Mutex 串行化），**禁止在多处直接读写文件**。
- 将来若需要复杂查询（分页、全文检索）再引入 Room，**上层接口不变**。


### 7.7 媒体与系统权限
- **图片选择**：使用 ActivityResultContracts.PickVisualMedia（系统相册选择器），**不需要任何存储权限**（这是关键，别去申请 READ_MEDIA_IMAGES）。
- **录音**：RECORD_AUDIO 运行时申请；MediaRecorder 配置 AAC-LC / MPEG_4 / 单声道 / 16000Hz / 32000bps / 20 秒定时自动停止；录音同时每 50ms 采一次 maxAmplitude，归并成 32 个峰值放进 peaks。
- **播放**：MediaPlayer 播本地缓存文件；播完自动复位；同时只允许一条语音播放（新播放打断旧的）。
- **自定义表情包**：从相册选图或拍照 → 压缩到长边 512px → 存 filesDir/stickers/ → Room 记一条 StickerEntity。

### 7.8 进程内事件总线（AppEvents）
- 单例 object，内含 MutableSharedFlow<AppEvent>（replay = 0，extraBufferCapacity = 32）。
- 事件类型：OverlayShown(mid)、AckReceived(mid, state)、ConnectionStateChanged(peerUid, state)、MessageInserted(mid)。
- UI 与服务都通过它通信，**不引入 EventBus 之类的第三方库**。

### 7.9 错误与崩溃防守（验收项）
- 任何进入服务的字段都当作**不可信输入**：长度、类型、范围全部校验（例如 peaks 必须为 0..1 的 32 个浮点；url 必须 https）。
- 全局 CoroutineExceptionHandler + 顶层 try/catch，**任何单条消息的解析失败都不允许影响服务运行**。
- 网络线程绝不做 UI 操作；UI 线程绝不做 IO。

## 8. Android 15 / 16 保活与权限适配（**决定项目成败的一章**）

### 8.1 权限清单（AndroidManifest.xml 顶部）
~~~xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_SPECIAL_USE" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.SYSTEM_ALERT_WINDOW" />
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
<uses-permission android:name="android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS" />
<uses-permission android:name="android.permission.RECORD_AUDIO" />
~~~
**注意**：SYSTEM_ALERT_WINDOW 是**特殊权限**，不能在运行时用 requestPermissions 申请，只能跳设置页；RECORD_AUDIO 与 POST_NOTIFICATIONS 是运行时权限。

### 8.2 前台服务类型：**避开 Android 15 的 6 小时限制（关键）**
- Android 15（API 35）起，dataSync 类型的前台服务**每 24 小时最多运行 6 小时**，到点会被系统强制停止 —— 这对"全天候收消息"是致命的。
- **解决方案：使用 specialUse 类型**，并声明子类型说明。侧载分发不经过 Google Play 审核，因此 specialUse 不会被拒：
~~~xml
<service
    android:name=".service.LinkService"
    android:exported="false"
    android:foregroundServiceType="specialUse">
    <property
        android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE"
        android:value="peer_to_peer_message_relay: keeps a websocket/ndjson stream open to receive peer messages in real time" />
</service>
~~~
- **不要用 dataSync**（6 小时必被停）。**这是硬性要求**。
- 同理，Android 15 限制了 BOOT_COMPLETED 广播启动 dataSync / camera / mediaPlayback / phoneCall / mediaProjection / microphone 类型的 FGS；**specialUse 不在限制名单内**，因此开机自启仍可用（8.5）。

### 8.3 启动与生命周期规则
- 必须用 ContextCompat.startForegroundService() 启动，并在 **5 秒内**调用 startForeground()（否则 ANR/崩溃）。做法：onCreate 里立刻 startForeground，网络连接放到协程里异步做。
- onStartCommand 返回 START_STICKY。
- 服务被系统杀死后由系统重启时，**不要依赖 Intent 携带的数据**，所有状态从 Room/DataStore 恢复（幂等重启）。
- **不要**在 onTaskRemoved 里 stopSelf()（那会让"划掉后台"就再也收不到消息）。
- 通知渠道：IMPORTANCE_LOW（无声，但可见、可下拉）；setOngoing(true)；setShowWhen(false)；setOnlyAlertOnce(true)。


### 8.4 常驻通知文案（要求：随时间问候 + **有趣** + 不显示未读数）

**设计目标**：这条通知每天会被看到几十次，所以它必须**像一个小活物**，而不是一句冷冰冰的"保持连接中"。但它不能吵（无声、不弹窗、不亮屏），也不能撒谎（状态必须真实）。

**文案 = 三段拼装**
1. **主问候（必选）**：从当前时间段的变体池里随机取一条 —— 池子见 附录 B.1。
2. **数据彩蛋（约 30% 概率叠加，让通知"活着"）**：用**本机真实运行数据**生成，例如"今天已经帮你弹了 7 个气泡"、"我已经守了 4 小时 12 分"。数据源与句式见 附录 B.3。
3. **状态副词（固定）**：连接正常 / 正在重连 / 连接失败，措辞见 附录 B.2。

**刷新规则（必须按此实现，否则会闪、会烦）**
- 每小时刷新一次。**同一小时内文案必须稳定**：用 `seed = epochHour` + "最近 8 条 LRU 去重"来选句，**不要在每次 notify 时重新随机**（否则连接状态一变文案就跳字，观感很差）。
- 连接状态变化时**立即刷新，但只换状态副词，主问候不变**。
- 最近 8 次出现过的句子不再选；池子抽干则清空 LRU 重新开始。
- 文案总长度（含昵称）**不超过 24 个字符**；超出时回退到同组的短句，避免被系统截断成半句。
- **深夜（23:00–04:00）只从"安静组"取词**，不卖萌、不吵人。
- **硬约束（用户明确要求）**：文案里**禁止出现** topic 名、uid、未读数，以及任何"你有 N 条未读"的表达。

**状态纪律（唯一不能开玩笑的地方）**
- 连接正常 → 可以俏皮；重连中 → 可以自嘲；**连接失败 → 必须清楚且可操作**（"点我救一下"），不许用玩笑掩盖故障。

**实现约束**：统一由 `NotificationFactory.build(nowMs, connState, stats): NotificationText` 产出文案，**禁止在 UI 层或 Service 里散着拼字符串**；文案池作为常量表集中存放（附录 B）。


### 8.5 开机自启
~~~xml
<receiver android:name=".service.BootReceiver" android:exported="false">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
        <action android:name="android.intent.action.MY_PACKAGE_REPLACED" />
        <action android:name="android.intent.action.QUICKBOOT_POWERON" />
    </intent-filter>
</receiver>
~~~
- 收到广播后启动 LinkService（specialUse 类型允许在 boot 后启动）。
- 若启动 FGS 抛 ForegroundServiceStartNotAllowedException → **捕获并降级**：发一条普通通知"点我恢复接收"，绝不崩溃。
- 另建议：用户手动杀掉 App 后，系统不会自动重启，**由用户在权限向导里被明确告知**这一点。

### 8.6 电池优化与 Doze
- 权限向导里引导加入白名单（isIgnoringBatteryOptimizations 检测）。
- 即使未加白名单，前台服务仍基本可用；但 Doze 深度休眠时网络可能被延迟，**这是系统行为，不是 bug**，UI 上不要谎报"已连接"——用真实心跳判活（见 6.8）。
- **不申请** WAKE_LOCK 常驻（耗电且不必要）；仅在单次附件下载（最多 15MB）时临时申请 PARTIAL_WAKE_LOCK 并在 finally 释放。

### 8.7 国产 ROM 适配（小米 / 华为 / 荣耀 / OPPO / vivo）
- 权限向导第 4 步：尝试跳转各家"自启动管理""后台弹出界面""电池 → 应用省电策略 → 无限制"。
- 跳转 Intent 全部用 try/catch 包裹，**任何跳转失败都降级为图文说明**（不同 ROM/版本组件名不同，跳转失败是常态）。
- 明确告知用户：需要在"最近任务"里**锁定本应用**（加锁图标），否则划掉即断。

### 8.8 通知渠道划分（共 3 个）
| 渠道 | 重要性 | 用途 |
|---|---|---|
| 常驻连接 | IMPORTANCE_LOW，无声 | 前台服务通知（问候文案） |
| 回执提醒 | IMPORTANCE_LOW，无声 | "某某 点掉了你的消息" |
| 降级消息 | IMPORTANCE_DEFAULT | 无悬浮窗权限时的消息兜底通知 |

### 8.9 网络状态监听
- 用 ConnectivityManager.registerDefaultNetworkCallback 监听 onAvailable / onLost；onAvailable 时**立即重置退避并重连**。
- 不要用已废弃的 CONNECTIVITY_ACTION 广播。

### 13.3 开发中发现并修复的真实缺陷（**已写进代码注释，别再犯**）
1. **HTTP 头不能放中文**：把中文昵称塞进 Title 头会让 OkHttp 抛 Unexpected char 0x6d4b。→ 改用 ntfy 的 **JSON 发布**（POST 根路径，topic/title 放 body，UTF-8 无限制）。
2. **keepalive 的 id 不是消息 id**：把它当 since= 锚点会让服务端回放旧消息（实测重启后又弹了一遍两小时前的消息）。→ 只对 event=message 记录 lastServerId。
3. **等附件下载完才弹框太慢**（实测 4.3 s）。→ 先弹占位框（"正在接收图片…"），下载完成后 attachImage 原地替换，不重新排队、不闪烁。
4. **占位文案没清掉**：替换图片时忘了清 text，图片下方残留"正在接收图片…"。→ 成功时清空 text、失败时换成过期提示。
5. **ComposeView 放进 WindowManager 必须自备 LifecycleOwner**（OverlayLifecycleOwner），否则 Compose 直接崩。
6. **matchParentSize 不能单独 import**（它是 BoxScope 成员函数）；**Modifier.blur 优于 RenderEffect**（API 31+ 自动生效、以下自动忽略，避开 API 名称差异）。
7. **targetSdk 36 强制边到边**：所有页面根布局必须加 safeDrawingPadding()，否则标题会被状态栏压住（实测踩过）。
8. **悬浮窗 x/y 被状态栏高度顶下去（实测 141px）**：不加 FLAG_LAYOUT_IN_SCREEN 时，WindowManager 把 x/y 当作「内容区坐标」，再叠加状态栏高度 → 窗口实际位置比 mAttrs 报的下移 141px，**所有点击都打偏**（现象极像「悬浮窗收不到触摸」）。排查：adb shell dumpsys window windows 里对比 mAttrs 与 Frames 行的 frame 是否一致。修复：气泡/球/面板三个悬浮窗全部加 FLAG_LAYOUT_IN_SCREEN。
9. **悬浮窗里的 Compose 手势收不到事件**：WRAP_CONTENT 的 overlay 窗口里，触摸能到窗口（原生 OnTouchListener 有回调），但 Compose 的 clickable / pointerInput 不触发。→ 悬浮球的点击与拖动改用**原生 OnTouchListener + MotionEvent**（含 scaledTouchSlop 判定），Compose 只负责绘制。
10. **二进制文件从 App 私有目录取出**：adb pull 读不到 files/ 下的文件；用 `adb shell run-as <包名> ls files/voice` 找到文件名，再用 `cmd /c "adb exec-out run-as <包名> cat <file> > 本地文件"` 取出（**必须让 cmd 做重定向**，PowerShell 的 > 会按文本解码而损坏二进制）。
11. **生成邀请码后必须订阅该邀请 topic**：否则朋友的 hello 永远收不到，配对永远完不成（现象：列表里一直显示「待对方加入」）。修复：订阅集合 = 开发 topic + 好友 topic + **待配对邀请 topic**（用 combine 合并 peers 与 pending 两个 Flow）。

## 17. 上传到 GitHub（含本机 hosts 屏蔽的绕行方案）

### 17.1 遇到的真问题：hosts 被写入 GitHub 屏蔽
本机 `C:\Windows\System32\drivers\etc\hosts` 里有一段由某个 App 写入的规则（注释为 "GitHub hosts (added by Doubao, video method 1)"），
把 **26 个 GitHub 域名全部指向 127.0.0.1**：github.com、api.github.com、raw.githubusercontent.com、objects.githubusercontent.com 等。
后果：`git push`、Release 上传、浏览器访问 GitHub 全部失败（表现为 TLS 握手错误或连接被拒）。

### 17.2 无需管理员权限的绕行（本项目采用）
让 git / curl 跳过 DNS，直接指定真实 IP：

```powershell
# 解析真实 IP（用公共 DNS，绕过 hosts）
Resolve-DnsName github.com -Server 223.5.5.5 -Type A

# 写进本仓库 .git/config，之后所有 git 命令都不再需要额外参数
git config --add http.curloptResolve github.com:443:20.205.243.166
git config http.schannelCheckRevoke false
```

实测真实 IP（2026-10-25）：github.com 20.205.243.166、api.github.com 20.205.243.168、
codeload.github.com 20.205.243.165、objects.githubusercontent.com 185.199.108.133、uploads.github.com 20.205.243.161。
IP 可能变化，`scripts/refresh-github-ip.ps1` 可一键重新解析并写回配置。
curl 侧对应 `--resolve host:443:IP`。

### 17.3 彻底修复（需要管理员权限，尚未执行）
```powershell
$hosts = "$env:windir\System32\drivers\etc\hosts"
Copy-Item $hosts "$hosts.bak"
(Get-Content $hosts) | Where-Object { $_ -notmatch "github" } | Set-Content $hosts -Encoding ASCII
ipconfig /flushdns
```

## 附录 D — 术语
- **信封（Envelope）**：我们自定义的 JSON 消息格式，装在 ntfy 消息正文里。
- **topic**：ntfy 的频道名，本项目中等同于"一对好友之间的私有通道"，**是密码**。
- **两段式发布**：先 PUT 上传文件，再 POST 信封引用它。
- **delivered**：对方客户端**成功弹出气泡**（不是"服务器收到"）。
- **dismissed**：对方**手动点掉气泡**（5 秒超时不算）。
